# Player account cloud contract

Status: implementation specification, not a deployed feature or executable migration. Reviewed 2026-11-07 against checkout `feat/player-account-save-foundation-20261107`. No remote writes, credentials, emails, or Auth configuration changes were made. The existing projects/table health and unused legacy table counts are parent-provided findings, not independently rechecked here.

## 1. Product boundary

- Email OTP and Google sign-in; play as a local guest before signup. Do not create Supabase anonymous users for the ordinary guest path.
- Three slots per account, each containing one complete playable state. First signup adopts the current valid guest state automatically; never overwrite an existing account slot automatically.
- Divergent local/cloud states require a player choice. Preserve the nonchosen complete state before changing the chosen authority. No timestamp-based winner, field merge, or wallet/Reader progress merge.
- One active gameplay session per account. A completed new player login fences the previous session. Token refresh, browser focus, retry, or an old session reopening must never take ownership back.
- No supported offline gameplay. Local journaling protects against interrupted requests; it does not grant permission to continue offline indefinitely.
- Cloud checkpoints: story start, story end, approximately every 30 minutes of active freeplay, plus best-effort exit. Session validity checks run separately and much more frequently.
- Membership/entitlements are server-managed account data, never imported from player save JSON. In-game wallet balance is game state, not membership/payment authority.

## 2. Existing runtime implications

`src/center/runtime/playerSave.ts` has `_version: 2`, but it is only part of the save: scene positions, story clock/time, orders/payment receipts, salary receipts, phone notes/history, notifications and scene state live there. Reader progress/publication and other logical keys are managed by `src/services/saveEntryService.mjs` and `src/save-session.mjs`.

The active authority is `persistent-era-1`, protocol 2, with independent local revision and generation, a synchronous atomic journal, and cooperating Web Locks. Preserve these guarantees. `accountSaveStorage.mjs` is a synchronous namespaced facade, not encryption or authentication. `accountSaveSlots.mjs` deliberately leaves quota to its caller. Neither is a cloud implementation.

Cloud export must be a new explicit codec, not `JSON.stringify(localStorage)` and not just PlayerSave. Do not upload or restore journal `sources`, `archive`, pending transactions, retired-test backups, auth tokens, analytics, browser preferences unrelated to play, or account namespace metadata. Retired historical reset data remains immutable evidence, never a source of recovered active progress. Existing `public.profiles/world_state/reader_state` stay untouched; do not adapt the single-user `world_state` primary key into multi-slot storage.

Proposed versioned portable envelope:

```ts
type PortableSaveV1 = {
  format: 'newtone-player-state';
  formatVersion: 1;
  saveEpoch: 'persistent-era-1';
  localProtocolVersion: 2;
  generation: { id: string; sequence: number };
  localRevision: number;
  values: Record<string, string>; // exact active logical values; includes Reader
  recoveryHolds: Array<{ domain: 'cafe'; release: 'verified-return-to-cafe-space' }>;
};
```

Use the intersection of service-approved logical keys and runtime-writable keys, with an explicit versioned allowlist. `newtone-layout-*` is runtime-writable but not currently accepted by `isServiceLogicalKey`; do not silently expand the cloud allowlist to cover it. Validate PlayerSave plus Reader/publication consistency using the existing strict save validation, not sanitization that silently turns malformed data into a new game. A cloud download is installed through a new service import transaction with fresh local provenance/receipts, not by replacing authority underneath an open facade. Preserve payload generation identity; preserve any displaced local generation in a backup. Pin and validate referenced publication/content compatibility before play.

Separate cloud synchronization metadata outside the strict local authority object: owner UUID, slot UUID, last acknowledged cloud revision/hash, the local snapshot/hash that acknowledgement covers, immutable pending request and operation UUID, chosen conflict decision. Do not add fields to `validateAuthority` without an explicit protocol migration. A cloud acknowledgement for local revision N must not mark subsequent local revision N+1 clean.

## 3. Tables and constraints

New data belongs in an unexposed `player_private` schema, not the existing admin `private` schema. All tables enable RLS as defense in depth. Browser roles get no table CRUD privileges. A dedicated NOLOGIN function-owner role receives only the exact player table privileges and read access needed for Auth identity/session checks, with owner-scoped RLS policies. Auth grants are column-scoped reads only: auth.sessions(id,user_id,created_at) and auth.users(id,is_anonymous); never refresh tokens, passwords or identity secrets. Do not make it BYPASSRLS or grant access to content admin tables. Privileged implementations live in `player_private`; thin public SQL SECURITY INVOKER wrappers call them. Both layers explicitly revoke default PUBLIC/anon EXECUTE and grant only intended authenticated entry points. Grant authenticated schema USAGE only as needed to call the private implementation, but never expose that schema through PostgREST. Every implementation repeats all identity/fence checks even when called without its wrapper. Use `SET search_path = ''`, fully qualified relations and functions, no dynamic SQL, no caller-provided owner ID.

Logical schema (all timestamps generated on server, revisions serialized as decimal strings in JSON to avoid JS bigint precision loss):

1. `player_accounts`: `user_id uuid PK REFERENCES auth.users ON DELETE CASCADE`; `active_auth_session_id uuid NULL`; `active_login_created_at timestamptz NULL`; `login_high_water_created_at timestamptz NULL`; `login_high_water_session_id uuid NULL`; `fence bigint NOT NULL DEFAULT 0 CHECK >= 0`; `lease_until timestamptz NULL`; `created_at`, `updated_at`. Retain the login high-water mark after release/expiry. Do not FK active session to auth.sessions: Auth cleanup must not erase fencing history.
2. `player_slots`: `(user_id, slot_no smallint)` PK; CHECK slot_no BETWEEN 1 AND 3; `slot_id uuid UNIQUE NOT NULL`; unique `(user_id,slot_id)`; `revision bigint NOT NULL CHECK >= 1`; `payload jsonb NOT NULL`; `payload_hash text NOT NULL`; `updated_at`; `last_operation_id uuid`; `save_epoch text CHECK = 'persistent-era-1'`. User FK. An initialized slot is created atomically with payload at revision 1; absence means empty. Slot UUID is immutable. No direct delete endpoint for v1. Creating a fourth slot is structurally impossible even under parallel requests.
3. `player_save_backups`: `backup_id uuid PK`; `user_id`; `slot_id`; `operation_id`; `kind` enum/check (`cloud-before-replace`, `local-not-chosen`, `cloud-before-restart`); `source_revision bigint NULL`; `payload`, `payload_hash`, `created_at`; unique `(user_id,operation_id,kind)`. FK `(user_id,slot_id)` to slots. Immutable. No browser delete/update. Ordinary checkpoint updates need not create backups; conflict resolution/restart always do. Backup retention has no automatic eviction in v1. If storage budget is exceeded, block destructive replacement rather than lose the nonchosen branch. A retention policy is a separate product decision.
4. `player_operations`: `(user_id,operation_id)` PK; `kind`, `request_hash`, `result jsonb`, `created_at`; mutation receipts committed in the same transaction as the mutation. Successful receipts have no TTL in v1. A repeated UUID with different arguments is rejected. Hash includes operation name, slot, expected revision, payload, chosen branch and adoption ID; excludes access token and transport session/fence, allowing the same account to reconcile a committed request after genuine reauthentication. Authorization is rechecked before returning receipts.
5. `player_guest_adoptions`: `(user_id,guest_generation_id)` PK; `adoption_id uuid`; `snapshot_hash`; `slot_id`; `operation_id`; `created_at`. Unique `(user_id,adoption_id)`. This deduplicates even when buggy callers generate a new operation UUID. Same generation with changed snapshot cannot silently allocate a second slot. It returns ADOPTION_ALREADY_COMMITTED with the original receipt and snapshot hash; a changed snapshot is not treated as uploaded. Later guest progress must explicitly reconcile with that slot.
6. `player_entitlements`: owner user UUID + entitlement code PK, server validity dates/source; privileged billing/admin writer only. Separate endpoint for self-read if needed; no save-write privilege can modify it.

Request validation: envelope version/epoch, nonempty required player value, valid types and bounded numbers, explicit key allowlist, consistent Reader data. Proposed cap is 2 MiB of UTF-8 canonical envelope, configurable only server-side after measuring real snapshots. Reject oversized/deep JSON before expensive processing at the API boundary and again in SQL. Compute SHA-256 on the server from `payload::jsonb::text` UTF-8, returning that digest as an opaque cloud equality token. Client comparison uses the stored acknowledged token and stable local codec digest, not an assumption that JS canonical JSON equals PostgreSQL JSON formatting. PostgreSQL digest schema depends on installed pgcrypto; qualify it after inspection. Hashes detect equality/corruption, not legitimacy or anti-cheat.

## 4. Identity and session fencing

Every operation derives UID from `auth.uid()` and session UUID from `auth.jwt()->>'session_id'`, rejects missing/malformed claims, verifies a matching live `auth.sessions(id,user_id)` row, and rejects anonymous Auth users (check authoritative auth.users.is_anonymous, not only Postgres role). Never authorize with user_metadata. Enforce configured application max lifetime separately if required: presence in auth.sessions alone is not proof that Auth timeout cleanup has happened.

Login and gameplay are a two-phase protocol. `verifyOtp` / Google callback obtains Auth tokens; `player_activate_session` completes player login. The UI says login/play is ready only after activation succeeds. Refresh and `INITIAL_SESSION` resume call status/renew, never takeover. Do not use generic SIGNED_IN events as fresh-login evidence; SDK events can repeat on focus.

`player_activate_session(operation_id)`:

- Ensure account row exists, then lock it FOR UPDATE. All other player RPCs take this same account lock before locking a slot. This serializes takeover, saves, slot quota, and adoption.
- Load caller's auth.sessions.created_at from the server. Require caller to be newest live session ordered by `(created_at,id)` for this user, not client clock/JWT iat/last refresh. Deterministic UUID tie-break is only for identical server timestamps.
- Compare `(created_at,id)` against the durable high-water pair. Smaller means SESSION_REPLACED even if the previous newer Auth row has since been deleted. Equal + same active session is an idempotent resume, not a new fence. Equal but released/replaced is denied: a genuine new login is needed.
- A strictly newer pair sets the high-water mark, active session and increments fence, with initial 90-second lease. Return fence as string, serverNow, leaseUntil. Same-session retry returns current lease/fence without incrementing.
- Logout/release clears active session and lease, increments fence, and retains the high-water pair. Old refresh cannot reactivate it.

`player_renew_session(fence)` checks identity, exact active session/fence, latest live session and high-water, then extends lease. Every save/read RPC uses these same checks and requires a live lease. Propose heartbeat every 30 seconds, lease 90 seconds, pause immediately on known offline/auth/SESSION_REPLACED and before the client lease safety deadline if checks fail. A lease that merely expired can be renewed only by the still-active same session/fence after a server check; expiry alone never transfers ownership. Do not conflate freeplay upload interval with heartbeat interval.

Checking latest live Auth session on every gameplay RPC blocks an old session as soon as a newer Auth row is visible, even before activation finishes. The durable takeover guarantee linearizes at the account-locked activation transaction: an old save already holding the lock may finish before takeover, but no old save may commit after takeover. Auth issuance and player activation are separate transactions; strict instantaneous fencing at raw OTP issuance is not claimed. Avoid triggers on Supabase-managed auth.sessions for v1. If the product requires atomic fencing at raw Auth issuance rather than completed player login, that needs an additional tested server Auth integration, not a client boolean.

Physical device IDs are advisory only; session_id is the authority. A copied token can impersonate its session; this contract is not hardware attestation. Same-browser tabs share Auth sessions, so keep the existing exclusive Web Locks. A disconnected old screen may stay visible briefly; it cannot save after fencing. Instant remote termination of already-running client JavaScript is impossible. If every local action must be server-authorized, action-gated networking is required; lease-based UI stopping is a bounded UX compromise.

Admin/content access stays governed by the existing owner allowlist, never by player signup or email domain. Prefer separate admin/player Auth storage keys to avoid replacing UI state accidentally. Because the server sees sessions on one project/user, a genuinely new admin login under the same UID is also a newer Auth session under this simple policy. Use a separate admin identity or explicitly design an independently verified session-purpose registry before promising otherwise; a client-supplied purpose label is insufficient.

## 5. RPC wire contract

All successful responses include `{ok:true, serverNow, fence, ...result}`; logical failures `{ok:false, code, retryable, ...safeDetails}`. Authentication/permission failures also use appropriate API errors. No payload in logs. Codes: AUTH_REQUIRED, SESSION_REPLACED, SESSION_EXPIRED, SESSION_NOT_ACTIVE, SLOT_NOT_FOUND, SLOT_LIMIT, SLOT_OCCUPIED, REVISION_CONFLICT, IDEMPOTENCY_MISMATCH, ADOPTION_ALREADY_COMMITTED, INVALID_PAYLOAD, UNSUPPORTED_SAVE_EPOCH, BACKUP_REQUIRED, BACKUP_CAPACITY, STORAGE_UNAVAILABLE. An unknown transport result is not a failure receipt.

- `player_session_status()` returns active/expired/replaced and current fence only for the caller session; does not acquire ownership.
- `player_list_slots(fence)` returns up to three metadata rows: slot_no, slot_id, revision, payload_hash, server updated_at, safe preview derived from payload. No cross-user selector.
- `player_read_slot(fence, slot_id)` returns payload and metadata under the same authorization. Backup list/read likewise require current session and derive owner.
- `player_create_slot(fence, operation_id, slot_id, slot_no, payload)` locks account; checks receipt, range and occupancy; validates; creates revision 1 plus receipt. Slot UUID chosen once client-side and persisted before request. Do not create a new UUID on timeout.
- `player_adopt_guest(fence, operation_id, adoption_id, guest_generation_id, payload)` locks account, validates identity/generation; checks receipts and adoption uniqueness; selects lowest free slot_no and creates revision 1, adoption mapping and receipt in one transaction. A full account returns SLOT_LIMIT without changing guest or cloud. New accounts naturally select slot 1. Existing account with space may adopt as an additional slot only through the explicit account-entry flow; never overwrite the selected existing slot. Guest generation must match envelope generation.
- `player_write_slot(fence, operation_id, slot_id, expected_revision, payload, reason)` where reason is story-start/story-end/freeplay/exit/manual-retry. Lock account then slot. Check receipt before CAS; validate payload; compare expected_revision to current. On mismatch return REVISION_CONFLICT with current revision/hash; do not mutate or auto-retry with latest revision. On match replace complete payload, increment cloud revision exactly once, compute hash, write receipt atomically.
- `player_resolve_conflict(fence, operation_id, slot_id, expected_revision, choice, local_payload)` pins the cloud branch by expected_revision. For `choice=local`, back up current cloud payload then replace with local at revision+1. For `choice=cloud`, back up local_payload, leave current cloud revision/payload unchanged, return chosen cloud payload and receipt. Both operations are one transaction. The client freezes/local-checks the exact local snapshot shown in the chooser. If local or cloud changes while choosing, reopen the comparison. Never mark cloud chosen before backup succeeds.
- `player_restart_slot(...)` is separate explicit UX and RPC, CAS + cloud-before-restart backup + new valid initial generation. No delete/recreate to bypass history or quota.
- `player_get_operation(fence, operation_id)` returns owned receipt or `not_found`; not_found is a momentary observation, not proof an in-flight request cannot later commit. Retry the exact immutable request safely or wait; do not manufacture a new operation ID while uncertain.
- `player_release_session(fence, operation_id)` invalidates only this active gameplay session. A stale release cannot invalidate a newer login. Store release receipt, but receipt lookup after release may require a new login. Sign out from Auth separately with local scope after successful release; do not globally sign out the newer device from the old one.

All mutations: account lock -> authorization/fence -> same-operation receipt -> slot/adoption checks -> validation -> CAS/backup -> mutation + receipt -> commit. A rejected conflict may be retried with the identical request after reconciliation only if unchanged; new user choice/new expected revision means a new operation UUID. Return mutation receipts as metadata, not ever-growing copies of every payload; conflict-choice-cloud replay can reference immutable backup/result revision and must reread latest cloud rather than assert that an old result is still current. Receipt replay reports the original result and separately current slot metadata.

## 6. Client order and recovery

1. Guest plays using the current local service. Signup begins by freezing/stopping the runtime writer under its existing lock, finishing any synchronous journal commit, validating a portable snapshot, and durably recording its guest generation/adoption UUID. Never freeze a half-committed pending transaction as a cloud save.
2. Run explicit OTP (`signInWithOtp`, then `verifyOtp` type email) or Google flow. Email templates must contain `{{ .Token }}`; signInWithOtp otherwise defaults to a magic link. Keep OTPs/tokens out of logs. Google callback resumes the same persisted adoption intent; do not start a fresh guest save on redirect.
3. Activate authenticated player session. On failure retain guest snapshot and stay at the account/connection gate. No account mount yet.
4. Adopt guest transaction or list/read existing account slots. On uncertain adoption retain original guest data and retry identical request; never clear guest based only on successful Auth. A full account requires a user choice to retain guest backup or explicitly replace a slot with backups. Automatic signup retention is guaranteed for a genuinely new account, not a license to overwrite a full existing account.
5. Validate downloaded/acknowledged payload; stage local account namespace + cloud metadata. Install via a new save-entry import/commit adapter under the global writer lock. Verify local write/read and committed receipt before switching active storage. Only then mark guest adoption complete. Keep the guest evidence until verified account installation; do not delete historical data as part of signup.
6. Before mounting gameplay, establish active session lease and acquire existing local writer locks. Scope in-memory access guard to UID + slot + auth session + fence + local session generation. Logout, account change, fence loss or expired lease stops old closures synchronously. Network success callbacks must recheck all these identifiers before touching local data.
7. Checkpoint captures an immutable local snapshot at revision N and persists its request/UUID before network dispatch. After response, persist ack that covers only N; newer local commits remain dirty. On timeout keep pending request, use receipt/retry. On CAS conflict stop syncing and show explicit choice. Local-only descendant of last acknowledged snapshot can upload by CAS; cloud-only advance with unchanged local base can download. Unknown ancestry or changes on both sides is divergence, regardless of timestamps.
8. Before installing chosen cloud data, back up displaced local data successfully on server via resolution RPC (and preferably local durable backup), close the old facade, import through the entry service, and reopen. Failure halfway keeps a pending import receipt and no running writer; resume that transaction, not guest fallback. If server chose cloud but local install fails, do not upload the stale local branch on next launch.
9. On connectivity loss persist current committed journal, stop progression, show reconnect state. Do not clear dirty data, simulate missed game time, or claim cloud sync. Resume only after session check and revision reconciliation. A replacement keeps unsynced local state as a recoverable branch for the next genuine login, never silently pushes it from the fenced session.
10. Normal logout: pause -> attempt pending sync/reconciliation -> release gameplay session -> local-scope Auth signout -> close facade/clear plaintext memory and account access -> guest landing. If sync failed, explicitly retain encrypted recovery state or offer a warning before discarding; never show successful cloud save. Offline logout must clear local credentials/access immediately, retain protected pending data if supported, and disclose that server lease expiry/revocation is pending. Do not replay a release after a newer session begins.
11. Exit is best effort only. Use a normal authenticated keepalive request if supported; sendBeacon cannot simply attach an Authorization header. Never put tokens in URLs or assume unload completes. Recovery uses the last acknowledged cloud snapshot plus protected local pending snapshot.

## 7. Local privacy and unresolved release gates

Namespacing is not logout privacy. Current plaintext localStorage can be read from DevTools or another same-origin script after logout. Encryption with a key saved beside ciphertext does not solve that. Membership, Auth identity and local storage access are separate concerns.

Recommended design to implement and test before claiming privacy: per-account encrypted durable snapshots in IndexedDB, AES-GCM with random unique nonce and AAD binding UID/slot/schema, unlocked only after server-authorized login; keep plaintext runtime in memory, explicitly flush encrypted durable journal, erase decrypted memory/key on logout. A server-held per-user wrapping key or platform-backed key-unlock strategy needs a separate threat model, provisioning/rotation/recovery contract and approval. Do not derive encryption keys from OTP, JWT or refresh token. WebCrypto non-extractable keys persisted in the same origin do not protect against hostile same-origin JS. This is not end-to-end encryption: the cloud save remains server-readable JSON by design.

The existing synchronous Storage + setItem verified-atomic contract cannot directly await IndexedDB/WebCrypto. An async durability adapter needs a deliberate journal protocol redesign and fault tests, or v1 must honestly expose plaintext local storage limitations. Clearing plaintext on logout is a possible privacy baseline only after successful cloud sync; it conflicts with preserving unsynced work unless the user approves loss or encrypted recovery exists. Do not claim both solved by accountSaveStorage.

Other launch gates: approved backup retention/storage budget; measured payload limit; maximum offline grace and whether heartbeat-bounded stop suffices; content-publication compatibility across devices; Google provider/redirect/SMTP/OTP templates and rate limits; identity linking policy tested against existing accounts; precise admin-vs-player session separation. None of these requires speculative remote changes during this design task.

## 9. Local implementation candidate added

The concrete, intentionally unapplied SQL is `docs/player-account-cloud-candidate.sql`, outside the migration runner. Client: `src/services/playerCloudService.mjs`; tests: `tests/playerCloudService.test.mjs`. Public wire endpoint is `player_cloud_v1(p_action text,p_args jsonb)` with actions activate/renew/list/read/receipt/create/adopt/write/resolve/release. This candidate implements the structural quota, account locking, identity/RLS boundary, durable login watermark, CAS, receipts, and conflict backups above, but is NOT a complete production migration. No psql, Docker or Supabase executable was discovered in this environment; PostgreSQL compilation, permissions and concurrent transaction tests remain required.

Candidate differences from the target contract:

- Payload is passed as `payloadRaw` plus `sourceFingerprint`, NOT a JSONB-reformatted digest. `serializePlayerCloudPayload` recursively sorts object keys; `fingerprintPlayerCloudPayload` hashes UTF-8 of the exact serialization. Server hashes the received raw text, verifies fingerprint, then parses JSONB. This supersedes the earlier cloud-hash proposal for candidate adoption binding. The portable snapshot includes the complete envelope and excludes retired archives/sources. The returned adoption receipt binds ownerId, slotId, operationId and sourceFingerprint. Store the exact portable snapshot/serialization in the local transfer ledger.
- `list` returns `autoAdoptionEligible` only when a server-issued unconsumed registration grant exists, no slots exist, and the durable adoption_claimed flag is false. The grant is issued only by AFTER INSERT on auth.users for a new nonanonymous row after this candidate is installed; there is no backfill. `adopt` rechecks/consumes the grant under the account lock, creates slot 1 and claims the account in one transaction. An old empty account without a registration grant returns EXPLICIT_ADOPTION_REQUIRED. Never infer new signup from signInWithOtp, local emptiness, metadata or a timestamp window.
- Candidate payload validation is structural + key allowlist + size/hash. Full semantic PlayerSave/Reader compatibility validation, publication compatibility, backup storage budget/restore endpoints, restart RPC, rate limiting and lifecycle cleanup remain release gates. A malformed-but-structurally-valid save can currently be stored; callers MUST validate before import and production must add semantic validation.
- Mutation receipts return the original committed revision, not current head. A replay or operation lookup must be followed by read/list before mounting. ClearPending injection must durably persist acknowledgement/import intent before clearing the exact pending operation. It must compare operation ID to avoid clearing newer queued work.
- Raw payload text is retained inside the receipt request for exact idempotency comparison. This is intentionally simple but duplicates save content; measure storage and replace with a collision-resistant request hash before production-scale use.
- JS service never performs Auth, automatic activation, automatic retries, conflict choice, import, or gameplay mounts. Explicit fresh-login handler calls activateAfterExplicitLogin; refresh/resume uses renew. Durable queue is an injected obligation, not an in-memory promise of persistence. Activation/renew response timing computes a conservative local deadline from server lease duration and request start. Application pause enforcement is still an integration obligation.
- SQL role is a new NOLOGIN executor with column-limited Auth reads, owner-scoped RLS and only required player-table grants. No service-role/browser secrets. Candidate uses built-in PostgreSQL SHA256(bytea), avoiding extension schema assumptions. Verify availability and execution privileges in the isolated target PostgreSQL version.

Verification performed: focused client unit tests (8 passed initially), not SQL execution. These tests do not prove SQL security or deployment readiness.

## 10. Composition, import, queue and sync implementation

Added `playerAccountBackend.mjs` as the actual injection-based composition adapter (no Auth calls). It exposes explicit login activation versus restored-session resume, list/adopt/create/read-recovery, local materialization, durable receipts, release, renew, stopped-state checks, closed-runtime `syncSlot`, and live-runtime `syncSnapshot`.

- `accountCloudImportService.mjs` + `accountCloudImportRecord.mjs`: strict full PlayerSave validation through the shared save-entry validator, portable envelope round-trip, no historical archive import, prepared immutable ledger before metadata/guard/authority, committed visibility last. Every write can persist then throw and be retried exactly. Existing playable targets are never overwritten. Normal slot creation counts prepared import reservations even before metadata. Save-entry Reader values are preserved; this does not add deeper Reader semantic validation absent from the original validator.
- Shared `validateSaveEntryAuthority` export and metadata visibility hooks were added by the parent implementation. Account slots now count cloud import reservations separately from guest adoption reservations. These are integration hooks, not a new runtime bypass.
- `playerCloudQueue.mjs`: each operation retains exact immutable request; acknowledgement is an atomic phase transition retaining request and receipt, not blind removal. Locks are per operation, separate from the gameplay writer lock. Unknown results stay pending. Same UUID with different body is rejected. Session tokens/fences are not accepted queue fields.
- `playerAccountBackend.mjs`: safe import of cloud-only slots; local/content comparison ignores only local journal revision, not game values or generation. Import, adoption, creation and successful receipt recovery preserve a cloud revision/fingerprint baseline. A changed local snapshot uploads only by CAS if the fresh cloud revision still equals that baseline. Changed cloud plus differing local state returns LOCAL_CLOUD_CONFLICT; no implicit cloud overwrite or merge.
- `syncSlot(slotId)` is for a closed runtime and takes the existing writer lock. `syncSnapshot(slotId,{payloadRaw,sourceFingerprint})` uploads an exact already-captured snapshot without modifying runtime storage. It advances the baseline only to that snapshot; subsequent local commits remain discoverable as dirty. Fresh server reads + CAS protect concurrent changes. Interval/story/exit calls are coordinator responsibilities.
- `recoverPendingCreate()` checks durable pending/acknowledged create records, retries the exact operation if outcome was unknown, and materializes its slot. ## 11. Registration-only automatic adoption hardening

The SQL candidate now includes a private `registration_grants` table and an `AFTER INSERT ON auth.users` trigger. Only a newly inserted nonanonymous user receives a grant. Existing Auth users are deliberately NOT backfilled, including empty accounts. Login, token refresh, metadata edits and anonymous-to-permanent UPDATE do not issue grants. Ordinary pre-signup guests remain local, so the supported signup path inserts a new nonanonymous account. Identity linking into an existing account is not a new grant.

The trigger has a separate NOLOGIN/NOINHERIT issuer role. It can INSERT only the user_id column of this table under an INSERT-only RLS policy, has no Auth reads or player-save privileges, and its function is not executable by public/anon/authenticated or the player RPC role. The trigger owner, not browser input, supplies NEW.id; NEW.is_anonymous must be exactly false. Its SECURITY DEFINER function uses an empty search_path and qualified table names. The player executor has owner-scoped SELECT and UPDATE only on consumption columns, no INSERT. No role membership or BYPASSRLS is granted.

`list` requires an unconsumed grant plus empty slots and unclaimed account. `adopt` locks the account, checks exact prior operation/adoption receipts first, then atomically consumes the grant, creates the slot/adoption record and writes the operation receipt. Invalid payload/slot errors roll back grant consumption with the rest of the transaction. Duplicate exact retries return the original receipt, not a new grant or slot. A grant with no eligible target returns EXPLICIT_ADOPTION_REQUIRED. Its existence is durable proof of a new registration after installation, not an inference from recent activity; it intentionally does not use a client-controlled age window.

Additional mandatory release verification: in an isolated Supabase stack create a nonanonymous user and assert exactly one grant; insert an anonymous user and assert none; create old users before migration and assert no grants after migration; update/refresh old identities and assert no grants; test Google new-user vs existing-user linking; test successful OTP confirmation and actual Auth insert field values; verify issuer column grants/RLS/trigger execute permissions; inject a trigger error and verify rollback/recovery. A faulty Auth trigger can reject signup, so this candidate MUST NOT be applied before these real PostgreSQL/Auth tests. Three static source-shape tests pass, but these are not SQL compilation, permission or transaction verification. SQL remains unapplied and unexecuted.
