## 1. 上次总结

上一轮已经确认 NewTone-V0.1 的 Landing → Reader 路径不再走旧 Reader preview 滑入方案，而是统一走 `ReadingTransition overlay`。旧 preview 残留已经清理，`inertPreview / previewPhase / previewScrollY / onPreviewReady` 不应恢复。

继续阅读语义已经明确：`lastScrollY` 是真实滚动位置，优先恢复；`lastReadPhase` 只是粗粒度 fallback；`maxReadPhase` 只是历史最高解锁进度，绝对不能再当书签使用。

上一轮还确认了 Landing 的 NewTone 是第一互动锚点：点击/触碰 NewTone 只负责唤醒标题、提示和反馈，不直接进入 Reader。真正进入 Reader 的语法仍然是向下滚动 / 移动端上滑。

本轮选择执行 A 方向：首次语言初始化层。B 方向“中枢入口显影”和 C 方向“正式 0.1 内容骨架”暂缓。

## 2. 本次完成

本轮完成了 A 方向的第一版闭环。

A1：首次进入判断与 overlay 接管已经成立。新增并接入 `hasInitializedLanguage`，首次进入时不直接进入 Reader，而是由 `ReadingTransition overlay` 接管语言初始化。确认完成后再进入 Reader；已有初始化记录的用户走原有过渡路径。

A2：首次语言初始化主流程已经成立。流程为：Landing 滚动 / 上滑 → ReadingTransition overlay → 文本层接入 → 当前语言确认 → 继续读取 / 是否变更 → 用户确认后进入 Reader。系统可以根据浏览器语言识别默认读取语言，但不会在用户未确认时自动进入 Reader。

A3：语言变更交互第一版已经收口。最初的 7 语言环形星图方案被废弃，改为更简单的“是否变更按钮承载当前语言 + 下方 2+3 语言阵列”。当前语言不出现在候选阵列中；候选语言只显示其它语言。桌面端以 hover 展开，移动端以 touch/tap 展开；点击外部区域可关闭。hover 语言只发亮，不切换；click/tap 语言才切换。

按钮系统也完成了关键收口：`继续读取` 和 `是否变更` 默认态同宽、同高、同边框、同文字颜色，交互态统一使用幕布式 hover。区别只在于：`继续读取` 幕布拉起后仍显示继续读取；`是否变更` 幕布拉起后揭出当前语言并展开候选语言阵列。

语言切换顺序已被修正：旧语言先淡出，新语言再淡入；标题与继续读取随后重组；语言阵列只交换“被点击语言”和“旧当前语言”的位置，其他语言不重排。这个修正避免了之前“全体语言一起乱、位置全部重排、像故障爆炸”的问题。

按钮入场的最终方向也已明确：不要继续叠外层弹入/抖动。按钮入场应拆成两段：先让空按钮框慢慢淡入，框稳定后再让按钮文字慢 scramble 出来。这样把“框”和“字”拆开，避免多套动画在同一时间抢节奏。

代码包检查结果：上传的 `package-lock.zip` 中没有包含 `node_modules` 或 `dist`，这一点是对的。`.gitignore` 里也已经排除了 `node_modules`、`dist`、`dist-ssr` 等构建/依赖目录。项目结构仍保持模块化：`components / views / stores / i18n / data / constants / styles` 分层清楚，没有看到需要立刻重构的整体混乱。

## 3. 本轮发现的问题

本轮最大问题不是功能做不出来，而是交互纠偏过程中浪费了很多时间。尤其是按钮和语言选择区域，原本可以更早通过真实 JSX/CSS 定位问题，但前期多次让实现侧“猜”视觉偏差，导致反复修错层级。

主要问题包括：

第一，默认态、hover 态、expanded 态被混在一起讨论。我们多次说“两个按钮不一致”，但截图里有时是默认态，有时是 hover 态，有时是 `是否变更` 展开后的状态。结果每一轮只修了一个状态，另一个状态又暴露出新问题。

第二，`继续读取` 和 `是否变更` 一开始被当成传统“主按钮 / 次按钮”处理。这个逻辑不适合当前界面，因为 NewTone 不是普通网页表单。两者应该属于同一组操作入口，只是职责不同。只有默认态完全打平、hover/expanded 都使用同一套幕布系统之后，视觉才开始统一。

第三，语言星图方案越修越复杂。7 语言环形星图一开始看起来符合“language orbit”的概念，但落到当前空间里会变成环形菜单、按钮轮盘或压缩过度的 UI。后面改成 5 语言 2+3 阵列后，方案反而更稳、更清楚。

第四，语言切换一开始被做成全体重组。点击一个语言后，标题、按钮、中心语言、外圈语言几乎同时 scramble，且语言列表重新 filter 导致位置重排。正确语义其实很简单：只交换“当前语言”和“被点击语言”，其他语言不动。

第五，按钮入场动画曾经叠了太多系统：整组 opacity、外层 `btn-signal-in`、文字 scramble、幕布 hover、文字切换。多套动画抢同一个时间窗口，导致按钮像弹入、文字像瞬间乱码完成，无法稳定调节。

第六，移动/桌面交互边界一开始不清。桌面端 hover 展开和移动端 tap toggle 混在一起，导致桌面端点击后语言层 sticky，点空白处也不关闭。后续通过区分 hover 设备和 touch 设备才修正。

## 4. 偏差原因

本轮偏差的根本原因是：过早在视觉描述层面反复微调，而没有及时切到结构诊断。

当某个 UI 问题连续 2 轮没有修对时，就不应该继续用“更亮一点、更慢一点、更像幕布一点”这种描述推动。正确做法应该是立刻要求输出真实 JSX、CSS、状态变量和动画参数，然后按状态拆开分析。

这轮按钮问题就是典型例子。最后发现问题并不只在颜色，而是涉及 wrapper 宽高、conditional render、外层 animation、文字 hook、hover/expanded 状态。前面如果更早要求输出 `.language-btn`、`.language-btn-signal`、`.lang-btn-curtain`、`showActions`、`useScrambleText` 的真实代码，就能少走很多弯路。

另一个偏差是把“炫酷特效”当成优先项。事实上，首次语言初始化层最重要的是流程语义：用户必须知道当前语言是什么、是否要变更、确认后才进入 Reader。特效只应该服务这个流程。只要特效干扰了状态判断，就应该先砍掉或降级。

还有一个偏差是没有尽早建立“状态验收表”。比如按钮至少应该拆成：默认态、hover `继续读取`、hover `是否变更`、expanded `是否变更`、语言切换中、语言切换后、收起后。前期没有这样拆，导致“两个框不一致”这个问题被反复泛化，最后每轮修的其实不是同一个状态。

---

## 5. 修正方向

以后遇到类似问题，必须按这个顺序处理：

第一，先确定交互语义，不先堆视觉。比如这次最终确定的是：两个按钮是同一套按钮系统；一个负责继续，一个负责变更；两者都用幕布，区别只是一个换字、一个不换字。

第二，连续两轮修不对时，立刻停止猜测，要求输出真实代码。至少要看 JSX 结构、外层 wrapper、className、关键 CSS、状态变量、动画参数。不要继续用自然语言反复猜。

第三，按状态分开验收。默认态只看默认态；hover 只看 hover；expanded 只看 expanded；切换语言只看切换流程。不要把多个状态混在同一句“看起来不一致”里。

第四，动画系统要少而清楚。按钮入场最终应采用“两段式”：空框先淡入，文字后 scramble。不要在同一层叠加 opacity、jitter、scale、scramble、幕布、文字切换。能拆开就拆开。

第五，语言切换只处理必要元素。用户点哪个语言，就只让该语言与当前语言交换；不要全体重排。标题和继续读取的重组应排在当前语言切换之后，不应抢先闪动。

第六，视觉复杂度要向第一版让步。A 方向的目标不是做最终视觉资产，而是完成首次语言初始化层的语义闭环。视觉只要达到“像 NewTone，不像普通设置页”，就可以封口。

## 6. 新增禁区

以下禁区为项目级长期禁区，不只是下一轮提醒：

不要恢复旧 Reader preview 滑入方案。

不要重新引入 `inertPreview / previewPhase / previewScrollY / onPreviewReady`。

不要重新创建旧用途的 `AppTransition.css`。

不要把 `maxReadPhase` 当继续阅读书签。

不要改变 `lastScrollY > lastReadPhase > maxReadPhase` 的恢复优先级。

不要让点击 NewTone 直接进入 Reader。

不要让语言选择完成后自动进入 Reader。

不要把语言选择做成 dropdown、settings panel、白底菜单、radio、checkbox 或国旗列表。

不要恢复 7 语言环形星图作为当前第一版方案。环形星图不是永远不能做，但当前版本不要做。

不要把语言候选列表每次用 `ALL_LANGS.filter(l !== language)` 重新生成并导致全体重排。语言切换必须只交换旧当前语言和被点击 slot。

不要让当前语言出现在候选语言阵列中。

不要让 hover 直接切换语言。hover 只能发亮或展开，click/tap 才能切换。

不要把桌面 click toggle 当成主要展开逻辑。桌面端以 hover 展开；touch 端才用 tap toggle。

不要让展开层在桌面端无法通过外部点击关闭。

不要让按钮默认态使用两套视觉系统。`继续读取` 与 `是否变更` 默认态必须同框、同色、同尺寸。

不要让按钮 hover 态使用两套系统。两个按钮都走幕布式 hover；一个换字，一个不换字。

不要在按钮入场时同时叠加外层弹入、scale 抖动、translate 抖动、opacity 抖动、文字 scramble。第一版用“空框淡入 → 文字 scramble”即可。

不要在一个视觉问题连续两轮失败后继续猜。必须要求输出真实 JSX/CSS/状态代码再判断。

不要为了“看起来酷”新增故障抖动。任何新增特效必须先确认不会破坏状态顺序和可操作性。

## 7. 待决事项

是否在未来重新引入更高级的语言星图：待决。当前第一版不要做。等正式视觉资产阶段，如果空间和交互都允许，再评估语言星图是否值得回归。

语言数量是否恢复到 7 个或更多：待决。当前 A 第一版以 6 个语言池、下方显示 5 个其它语言为主。`copy.js` 和 `progressStore` 中仍包含 `id`，但 `ReadingTransition` 当前语言池不使用 `id`。这不是立即问题，但后面如果要支持 Bahasa Indonesia，需要统一 `ALL_LANGS`、`detectLanguage` 和展示策略。

`detectLanguage` 当前只识别 `zh / en / ja / ko / fr`，没有识别 `es / id`。如果后续保留 Spanish 或 Indonesian，需要补齐浏览器语言检测。当前不影响 A 第一版闭环，但属于待补一致性。

是否拆分 `ReadingTransition.jsx`：待决。现在代码仍能工作，但 `LanguageInit` 逻辑已经明显变重。短期不建议立刻重构；如果后续继续扩展语言层，建议拆成 `LanguageInit.jsx`、`useScrambleText.js`、`LanguageOptions.jsx` 等小模块。

B 方向“中枢入口显影”如何出现：待决。需要决定入口是由阅读阶段触发、ReaderProgress 触发，还是正文关键节点触发。

C 方向“正式 0.1 内容骨架”如何挂载：待决。需要决定正文主线、records、perspectives、fragments 的最小职责边界。

## 8. 当前状态

A 方向：首次语言初始化层第一版基本完成。它已经可以承担“第一次进入 Reader 前的基础读取条件确认”职责。

当前已成立的链路是：

Landing 滚动 / 上滑 → ReadingTransition overlay → 文本层接入 → 空按钮框淡入 → 按钮文字 scramble → 继续读取 / 是否变更 → hover/touch 是否变更 → 语言阵列 → click/tap 语言 → 旧语言淡出 → 新语言淡入 → 标题/继续读取重组 → 点击继续读取 → Reader。

代码结构检查结论：项目整体仍保持模块化，没有看到需要立刻处理的结构性混乱。`src` 下的 `components / views / stores / i18n / data / constants / styles` 分层清楚。`ReadingTransition.jsx` 当前偏重，但尚未到必须立即拆分的程度。后续如果继续在语言初始化层上加功能，应优先拆分，而不是继续塞进同一个文件。

压缩包检查结论：`package-lock.zip` 没有包含 `node_modules`，也没有包含 `dist`。这是正确的。压缩项目时应继续排除 `node_modules` 和 `dist`。`.gitignore` 里已经有对应规则。

构建状态：用户侧反馈 build + lint 通过。我这边没有重新执行 build/lint，因为压缩包不含 `node_modules`，本地沙盒不能保证能离线安装依赖。我只做了静态结构检查和压缩包内容检查。

当前不建议继续无目的打磨 A。除非后续视觉验收发现严重问题，否则 A 可以作为第一版封口，进入日志归档。

## 9. 下一步规划

下一步不要直接同时开 B 和 C。建议先做一个极短的 A 收口验收：

1. 首次进入：确认标题、空按钮框、按钮文字、继续读取进入 Reader 都正常。
2. 语言变更：确认 hover 展开、外部点击关闭、旧语言淡出、新语言淡入、只交换被点击项。
3. 回归路径：确认老用户不再看到 LanguageInit，继续阅读仍按 `lastScrollY` 恢复。
4. 侧键/浏览器后退：确认不黑屏、不进入无 view 状态。

A 收口验收过后，再选择下一方向：

优先方向 B：中枢入口显影。理由是 A 已经补完进入 Reader 前的条件，下一步更自然的是让 Reader 读到某个阶段后通向 Center。B 的重点不是做完整 Center，而是做“入口如何出现”。

备选方向 C：正式 0.1 内容骨架。理由是如果当前更想推进内容，可以开始搭正文主线、records、perspectives、fragments 的最小骨架。但不建议先大规模写内容，否则系统入口还没接完时会造成内容和交互互相拖拽。

推荐顺序仍然是：

A 收口验收 → B 中枢入口显影 → C 正式 0.1 内容骨架。

本轮最重要的经验：以后不要让 AI 在复杂 UI 问题上长期猜。两轮没修对，就立刻要真实代码、拆状态、做最小修改。这个规则必须保留。
